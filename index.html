Executive recommendation

Four MCP servers, one governed architecture, 12 working days.

A senior AI engineer can deliver a functional pilot connecting Claude to OpenCaseLaw, Garmin, MyFitnessPal and TrainingPeaks in 12 working days, including authentication, access control, security and handover. The plan proves one public and one private pattern first, then repeats it.

What the client wants

Claude answers using authorised data from OpenCaseLaw, Garmin, MyFitnessPal and TrainingPeaks, with proper authentication and security, and without anyone copying data by hand.

What the 12 days prove

All four servers connected, per-user sign-in, two access groups, protected remote hosting, negative tests, a repeatable setup guide and a live demo.

What it does not claim

Not a production rollout, legal sign-off, a full security audit or guaranteed approval from Garmin, MyFitnessPal or TrainingPeaks for official API access.

How the 12 days are shaped

Build the two hardest patterns first, then replicate. About a quarter of the time is deliberate margin for the fragile parts.

Pattern first

Day 3 proves the simplest case: a public remote server with no credentials (OpenCaseLaw). Days 4 and 5 prove the hardest: personal data, login with MFA, stored tokens (Garmin).

Then replicate

Days 7 and 8 reuse the same gateway, policy and test method for MyFitnessPal and TrainingPeaks. Days 11 and 12 absorb overruns before documentation and the demo.

    MCP fundamentals
    
        
    MCP (Model Context Protocol) is an open standard that lets an AI assistant such as Claude discover and call external tools. Think of it as a standard plug between Claude and a business system.
    
      
    
      
    A question’s journey
    Step through what happens when someone asks “What was my average sleep this week?”
    
      
    

      
    What travels on the wire
    Claude and a server exchange short structured messages. Pick a message to see its role.
    
      
    
      
    

      
    The three building blocks
    
      
    
        
    Host
    The application the person uses, here Claude. It decides which tool fits the question and asks for consent where required.
    
        
    MCP server
    An adapter that offers tools, validates inputs and translates each call into the platform’s real API. It owns no data itself.
    
        
    Platform
    The system that actually holds the data and enforces its own permissions, limits and availability.
    
      
    

      
    Local or remote MCP
    The same connector can run on one person’s computer or on a server run by the firm. Switch to compare.
    
      
    
      
    
      
    

      
    Anatomy of a tool
    A tool is a named action the server offers to Claude. Hover or tap a part to see what it does.
    
      
    
        
    "name": "get_sleep_data",
"description": "Average and nightly sleep
  for the last N days",
"arguments": { "days": 7 },
"access": "read-only"
    
        
    Hover a line
    Each part of the definition has a job. The name identifies the tool, the description tells Claude when to use it, the arguments are what Claude fills in, and the access mode decides whether it can change data.

    Implementation stage
        
    
      
    
      
    
        
      
    
      
    
      
    Why this shape
    
      
    
        
    One door
    Users and administrators deal with one stable entry point. Rules, logging and tool filtering live in one place instead of being rebuilt per platform.
    
        
    Swappable parts
    Change the Garmin adapter from a community server to the official API without touching Claude or what users see. Use the stage switch above to see the change.
    
        
    Legal and fitness separated
    OpenCaseLaw needs no personal credentials. The fitness adapters only run with the user’s own tokens and only for the pilot group.
    
      
    
      
    Open point: the Microsoft 365 sign-in code already present in the client’s backend may be reusable for the gateway. This needs confirming on day 1, because it changes days 6 and 9.
    
    
    

    
    
    
      
    
        
    Delivery approach
    
        
    Do not build four connectors in parallel. Prove one public and one private pattern, check them against a gate, then repeat the pattern twice.
    
      
    
      
    
        
    Pattern A · public
    OpenCaseLaw
    A remote server that needs no sign-up or key. It validates Claude administration, remote transport, tool discovery and whether legal answers carry verifiable sources. Day 3.
    
        
    Pattern B · private
    Garmin
    Personal data, MFA login, stored tokens, a large tool surface to cut down, and a remote endpoint that needs its own protection. This is the hard case. Days 4 and 5.

    Handling credentials
    
      
    
        
    We should not receive
    • Real employee passwords by email, chat, tickets or source files
    • Shared cookies copied between people
    • Production health data before consent and retention are agreed
    
        
    Preferred handling
    • Test accounts signed in live during a short call
    • Secrets delivered through the client’s approved secret channel
    • Separate development and production credentials
    
      
    

      
    Data examples to request
    
      
    For each platform, five representative questions with expected fields, plus one empty-data case, one unauthorised case and one expired-session case. These become the acceptance tests on days 9 and 10.
    
    
    

    
    
    
      
    
        
    Security and access
    
        
    Legal search is for everyone in the firm. Fitness is for a selected group, named by email address. Each person connects their own account and nobody else can see it.
    
      
    
      
    View permissions as
        
    
      
    
      
    
      
    V1 is read-only. “Confirm first” applies only if write actions are approved in a later phase.
    

      
    How a personal account gets connected
    Step through the sign-in and token journey. Passwords and cookies are never shared between users.

    A request must pass every layer. Select a layer to see what it stops.
    
      
    
      
    
      
    

      
    What is stored
    
      
    
        
    Kept by the gateway
    • Per-user provider tokens, encrypted
    • Group membership from the firm’s directory
    • Audit entries: user, tool, time, allowed or refused
    
        
    Not kept by the gateway
    • Search text or fitness values returned to Claude
    • Shared passwords or shared cookies
    • Anything for users outside the allowed group
    
      
    
      
    What Claude itself retains depends on the firm’s Claude plan settings, to be confirmed with the plan owner.

    Why 12 days and not fewer
    The plan separates engineering effort from waiting time. Each risky task has margin built in.
    
      
    
        
    Margin on the fragile parts
    Garmin gets two days for login, MFA and one re-authentication cycle. Day 10 absorbs access-group surprises. Day 11 absorbs any overrun from MyFitnessPal or TrainingPeaks.
    
        
    Clock-start conditions
    • Claude Owner and IT contact available
    • Garmin test account populated, MFA reachable
    • Host, domain, TLS and secret store approved
    • Read-only scope and groups agreed
    
        
    The schedule stops or changes when
    • A provider requires approval before test access
    • Security requires a new identity integration
    • No representative account or data exists
    • Write actions or a production SLA enter scope
